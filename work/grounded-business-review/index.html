有据经营分析经营​周报：​找​异​动​原因，​每​个​数字​都​对​回​查询​结果

在一份合成的到店团购数据上，把“每周监控 → 按维度拆解 → 写经营周报 → 数字核对”做成一条可以重跑的线，并比较三种找原因的做法：固定规则的脚本、把固定查询结果交给模型的一次提示词、让模型自己用工具查数的 Agent。

一分钟看完

每周看经营数据的人要知道哪些指标异动、原因在哪；让模型找原因、写周报，原因找得准不准，周报里的数字能不能都对回查询结果（在合成数据上测）。

我在合成的到店团购数据上搭了指标字典、一条 SQL 的周监控、贡献度和率效应拆解、带数字核对的经营周报，比较固定脚本、一次提示词和 Agent 三种找原因的做法；埋好答案的测试题和评测计划在跑之前冻结；另把同一条流程搭成 Dify 工作流。

让模型自己决定查什么，原因找得最准，两个维度交叉的原因尤其明显；代价是第一稿更常引错行，费用约是一次提示词的 1.8 倍。固定脚本在单一原因上不差，这批题分不出它和 Agent 的高下。数字核对拦住了引错行的数，但对中文数字太严，把没有错数的周报也拦下了。

动手前以为的

以为一次提示词第一次交卷大多能过数字核对

评测数据说明的

第一次交卷只过了 19/36；最后没放行的都卡在中文数字上，没有一个错数

  • 34/36 Agent 原因全找对（一次提示词 28/36） 94.4%，95% 区间 81.9 至 98.5%
  • 0/6 两个维度交叉的原因，一次提示词答对的题 0.0%，95% 区间 0.0 至 39.0%
  • 19 Agent 第一稿数字对不上引用行的段落

局限

01数据、​埋的​事件、​监控​和​三​种​做法​都​出自​同​一个​项目

埋的事件干净，都落在现有维度里，真实的原因常常不是这样。建议：换到真实数据前，先拿历史上已经查清原因的周做一批题再测。

02Agent ​和​脚本​只差​几题​（p ​= ​0.45），​这​批​题​分​不出​高​下

建议：要分出高下得加题，尤其是两个原因和两个维度交叉的题。

03数字​核对​对​中文​数字​太​严

最后没放行的周报里没有一个错数，没过的段落都卡在“这两项”“前一天”这类词上。建议：把计数词和数量分开处理，或给计数词单独的规则；严到什么程度是产品上的取舍，要和使用的人一起定。

04Agent ​第一​稿​引了​不在​引用​行​里的​数的​段落​有 ​19 ​段，​靠​退回​改​一次​才​全部​改​好

没有核对就会发出去。建议：核对放在发出之前，不能省。

05建议​没有​打分

建议：给建议定评分规则，再在同一批题上测。
